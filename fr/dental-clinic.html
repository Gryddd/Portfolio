Praxis Dr. Luis IT Médicale & Support Distant MSP

Conception et exploitation opérationnelle d'une infrastructure de cabinet médical virtualisée selon les pratiques d'un prestataire informatique (MSP) allemand. Le projet associe un pare-feu périmétrique 4 zones sous OPNsense 26.7, un contrôleur de domaine Windows Server 2019 et un poste d'accueil avec support helpdesk via Zammad Cloud et RustDesk.

Environnement labo : VMware Workstation Pro · OPNsense 26.7 · Windows Server 2019 · Windows 10 Pro · Zammad Cloud · RustDesk Remote Support

Présentation du projet & Architecture des rôles

Environ 90 % des demandes de support dans les cabinets médicaux et établissements de santé sont traitées à distance par les équipes de niveau 1 et 2. Pour reproduire fidèlement ce modèle opérationnel, le laboratoire est physiquement divisé en deux environnements distincts :

  • Infrastructure du cabinet (Hyperviseur On-Premises) : Un environnement virtualisé sous VMware Workstation Pro hébergeant un pare-feu 4 zones (OPNsense), Windows Server 2019 en tant que contrôleur de domaine et un poste d'accueil Windows 10.
  • Poste de support technicien (PC portable externe) : Une station indépendante hors du réseau local du cabinet, réceptionnant les tickets via Zammad Cloud et assurant les télémaintenances avec RustDesk.
  • Segmentation réseau stricte : OPNsense sépare le réseau local du cabinet, le système de radiologie numérique et le réseau de télématique de santé sans interférence avec l'hôte physique.
  • Gestion centralisée du domaine : Windows Server 2019 administre le DNS, le serveur DHCP, les partages SMB et le montage automatique des lecteurs réseau par stratégies de groupe (GPO).

Topologie réseau logique & Zones

L'architecture réseau divise le cabinet en quatre zones isolées. L'interface WAN de FW01 reçoit son adresse dynamiquement via une liaison montante ISP simulée (VMware NAT). Le réseau local héberge le contrôleur de domaine et le poste d'accueil. Les réseaux de radiologie et de télématique sont isolés par des règles de pare-feu avec état.

  • WAN / FAI simulé : VMnet8 (192.168.74.0/24 NAT) · Passerelle 192.168.74.2 · FW01 WAN 192.168.74.128
  • LAN Cabinet : VMnet2 (192.168.10.0/24) · Passerelle 192.168.10.1 (em1) · DC : 192.168.10.10 · Accueil : 192.168.10.55
  • LAN Radio : VMnet3 (192.168.20.0/24) · Passerelle 192.168.20.1 (em2) · IP virtuelle : 192.168.20.50 (Port 445 SMB vers .10.10 uniquement)
  • Réseau Télématique : VMnet4 (192.168.40.0/24) · Passerelle 192.168.40.1 (em3) · IP virtuelle : 192.168.40.50 (Isolé par défaut)

Virtualisation & Pare-feu périmétrique OPNsense

La virtualisation repose sur VMware Workstation Pro. Afin d'éviter toute fuite de routage avec le système d'exploitation hôte, les commutateurs virtuels internes (VMnet2, VMnet3, VMnet4) ont été configurés en réseaux personnalisés avec les adaptateurs hôtes désactivés.

Afin d'éliminer les latences d'accès sur le disque SATA interne de 3 To, la gestion mémoire de VMware a été configurée pour verrouiller l'intégralité des 9,5 Go alloués directement dans la RAM physique de l'hôte.

Le pare-feu périmétrique et la passerelle par défaut s'appuient sur OPNsense 26.7 sous FreeBSD 14. À travers quatre cartes réseau virtuelles (em0 à em3), FW01 assure le routage, le NAT et le filtrage dynamique des paquets.

Active Directory & Services clés Windows Server

Le serveur SRV-PRAXIS01 (Windows Server 2019 Standard) joue le rôle de contrôleur de domaine pour la forêt « dr-luis.de » (NetBIOS: DR). Il prend en charge Active Directory, le DNS, le serveur DHCP et les partages de fichiers SMB.

La structure Active Directory est organisée en unités d'organisation (OU). Les comptes du personnel médical sont regroupés dans des groupes de sécurité administrant les droits d'accès aux partages.

Le service DHCP a été déployé par script PowerShell. La plage 192.168.10.0/24 attribue automatiquement les configurations réseau avec passerelle (Option 003 : 192.168.10.1) et DNS (Option 006 : 192.168.10.10).

Le stockage centralisé exploite des partages administratifs masqués (PraxisShare$, RoentgenShare$) pour éviter toute découverte non autorisée sur le réseau local, sécurisés selon le principe du moindre privilège.

Trois objets de stratégie de groupe (GPO) montent automatiquement les lecteurs réseau requis lors de l'ouverture de session utilisateur, avec ciblage précis au niveau de l'élément (Item-Level Targeting).

Poste d'accueil & Activité clinique

Le poste PC-REZEPTION01 (Windows 10 Pro) simule la station de travail principale de l'accueil. Intégré au domaine dr-luis.de, il reçoit dynamiquement son bail DHCP et ses paramètres DNS du serveur Windows.

Après authentification sur le domaine, l'utilisatrice accède directement aux répertoires partagés montés sous forme de lecteurs réseau dans l'Explorateur Windows.

Une imprimante réseau dédiée (Rezeptdrucker_Empfang) est configurée sur le poste pour l'édition rapide des ordonnances et feuilles de soins.

Support distant MSP, Billetterie & Gestion des incidents

L'assistance technique du cabinet est assurée via la plateforme de billetterie Zammad Cloud et des télémaintenances directes avec RustDesk. Chaque ticket respecte le principe de double documentation : notes techniques internes pour le diagnostic et réponse publique formulée avec courtoisie.

Trois scénarios d'assistance typiques d'un cabinet médical ont été validés en conditions réelles :

Incident 1 : Blocage du spouleur d'impression à l'accueil (Ticket #55002)

La secrétaire signale l'impossibilité d'imprimer des ordonnances urgentes. Le technicien prend la main via RustDesk, stoppe le service Spooler, vide les fichiers d'impression orphelins dans C:\Windows\System32\spool\PRINTERS et redémarre le service. Les impressions reprennent aussitôt.

Incident 2 : Verrouillage de compte suite à des erreurs de mot de passe (Ticket #55003)

L'employée Lisa Fronter ne parvient pas à se connecter le matin. Le journal des événements de sécurité du contrôleur confirme l'Event ID 4740. Le technicien déverrouille le compte dans Active Directory, attribue un mot de passe temporaire et force sa modification à la prochaine session.

Incident 3 : Validation de l'isolation du réseau télématique

Afin de vérifier les exigences de sécurité de santé, l'isolation du réseau télématique est testée. Une requête ICMP émise depuis le réseau local vers l'IP 192.168.40.50 est bloquée par défaut. L'ajout d'une règle de diagnostic temporaire confirme le routage avant retour à l'isolation complète.
